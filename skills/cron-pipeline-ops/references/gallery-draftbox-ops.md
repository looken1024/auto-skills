# 公众号图集 / 草稿线的运维记录

源起 2026-10-01~02 的图集线改造（贴图→图文 + 小程序链接 + 换话题池 + 草稿箱大清理）。
> 注：流水线本身的文档在技能 `wechat-ai-publisher`（**用户自有，curator 不能写**）；这里是运维侧的可复用经验。

## 1. 草稿箱批量清理

需求形如“除了最近两天的都删掉”。

1. `POST /cgi-bin/draft/batchget`（`no_content=1`，offset 步长 20）拉全量，每条取 `update_time`（unix 秒）。**`total_count` 与枚举数对得上才说明拉全了**；返回条数封顶 20/页。
2. 按“最近 N 天”切分：`datetime.fromtimestamp(ts) >= now - timedelta(days=N)` 保留。
3. **删之前先分类，把“不是流水线产物”的挑出来保护**：本号图集草稿 = `article_type == "newspic"` 或标题含“图集”；**用户手写的文章草稿 = `news` 且标题里没有“图集”**（本次挑出 14 条：三国/历史/社会类 + 3 条同名的「周末小习惯」）。这批列给用户确认，不自己删。
4. `POST /cgi-bin/draft/delete` 逐条删，`errcode=0` 即成功；每 25 条 sleep 0.3s。**删除不可恢复**。
5. 删完再拉一次 `total_count` 复核。

### 踩坑
- **分类规则别写窄**：第一版过滤器写成“标题含「图集」”，但**老图集草稿的标题就是纯话题名**（“秋天”“森林”“咖啡馆”）→ 只删掉 36/113。正解：`type == "newspic" or "图集" in title`。删前先打印分类清单核一遍。
- **后台页面计数可能对不上 API**：用户看到“还有 142 条”，而 API `total_count=49`（49 草稿 + 已发≈93）。本号 `freepublish/batchget` 报 `48001`，**拿不到已发表列表，验证不了后台那个数**——请用户截图/刷新页面，别硬猜。
- **发布后草稿会从草稿箱消失**：在草稿箱里找不到≠没建过（曾因此误判用户那篇文章“不是我们生的”）。

## 2. `process_image()` 的 OOM（2026-10-02 修，别回退）

- 症状：图集进程 exit `-9`，日志停在“下载完成”之后；`dmesg -T | grep -i "killed process"` 能直接看到。
- 根因：本机 ~2G 内存，原实现对**整图**调 `np.random.normal(..., arr.shape)`——float64 噪声数组在 2500×3750×3 上就是 225MB，加上加法/clip 的临时数组单张峰值 **500MB+**，9 张连跑必死。
- 修法：`float32` + **按行块（band=256）加噪**，`np.clip(..., out=blk)` 原地写，峰值降到 ~150MB/张。
- 运维：跑图集前先 `free -m`；可用内存 <300MB 时先清浏览器残留标签（`curl 127.0.0.1:9222/json/close/<id>`，本次一次关掉 27 个标签回收 ~400MB）。
- 通用教训：这类“图像滤镜流水线”在 2G 小机器上要把**逐像素运算改成分块 + float32 + 原地写**，不要留整图大数组。

## 3. 版式取舍：贴图 vs 图文（已定案）

- 微信草稿 `content` 能力：`newspic`（图片消息/小绿书）**只支持纯文本**；`news`（图文消息）**支持 HTML**。
- 所以“正文里一行字可点击跳小程序”**只能用 `news`**；用 `newspic` 写 `#小程序://` 是死文字。
- 代价：图集从「贴图」变成「图文消息」，版式不同了（用户当时就问过“我原来是贴图，现在怎么变成了图文”）。已向用户说明并确认：“要推小程序链接就只能用图文”。
- 已实测的写法细节（`<a data-miniprogram-appid=...>`、`uploadimg` 取正文图 URL、`draft/update` 不能改类型报 `53403`、`draft/batchget` 才是列草稿接口）见 `references/wechat-draft-api-content-types.md`。

## 4. 保留策略自动化（2026-10-03 起）

需求：“每天删 2 天前的草稿箱作品，同时把关键词删掉”。落地：`prune_drafts.py` + cron `e11f232f4c79`（每天 09:00，`no_agent=true`，包一层 `~/.hermes/scripts/prune_gzh_drafts.sh`）。

- 流程：`draft/batchget` 拉全量 → `update_time < now - N*86400` 的图集草稿 → `draft/delete` → 把对应话题从 `topics.json` **和** 脚本内置表同步摘掉。
- 话题解析：标题匹配 `^(.+)·每日图集（\d{4}-\d{2}-\d{2}）$` 取组 1；老式 `newspic` 草稿标题即话题（这类标题里没有“图集”二字）。
- 参数：`--days`（默认 2）、`--dry-run`、`--include-articles`。
- **2026-10-03 定案：cron 常态用 `--days 2 --include-articles`（图集 + 文章都清）**，job 更名「草稿箱清理-每天09:00（图集+文章）」。
- **每次跑都播报池子余量**（`pool_status(retired_today)`）：`话题池剩 N 个关键词（今天淘汰 X 个，按此速度还能撑约 D 天）`，`N < 40` 前缀 ⚠️。注意**每条退出路径都要打印**（草稿箱为空 / 无需改动 / dry-run / 正常删完），否则空箱子那几天恰好不报，用户会以为任务没跑。

### 关键：草稿箱里有两类东西，别一刀切
- 图集草稿 = 本流水线产出（标题带 `·每日图集（日期）`）。
- 文章草稿 = **cron `4b552ab71572` 每天 23:00 自动写好的稿**（三国/历史/社会类，只存草稿不群发，等用户手动发）。**之前误以为这些是用户手写的**——用户说要“文章也删掉”时是指这一批已过期的，不是让以后每天自动清文章。所以清理任务默认只清图集；连文章一起删必须先问用户。
  > 通用教训：草稿箱里“看起来像人写的”内容也可能是自己家 cron 产的。**先 `cronjob list` 看看有没有日更写稿任务**，再决定哪些能自动删。

**2026-10-03 定案：本号这两类现在都清。** 用户明确「把文章任务停掉，文章也需要清理」→ 先暂停日更 job `4b552ab71572`，再把包装脚本改成 `--include-articles`。话题摘除仍只对图集草稿生效（文章标题带不出话题）。
> ⚠️ 这份结论是**有前提的**：文章 job 已停。若哪天恢复日更写稿，清理任务要不要继续删文章必须**重新问用户**——那是「删掉已过期的旧稿」还是「每天自动清掉用户还没发的稿」，差别很大。

### 踩过的坑
- **同步两个数据源时必须两个都备份**：`sync_pool()` 第一版只给 `topics.json` 留了 `.bak`，测试时只还原了 json 没还原 `.py`，两个源立刻不一致（172 vs 170）。改成同时备份 `topics.json` + `pexels_gallery_draft.py` 后则可整体回滚。
- **双源一致性要用代码校验**，别凭记忆：正则抽 `.py` 里所有 `("cn", "en"),` 行成集合，与 json 的 `cn` 集合求对称差，应为空。
- **空池子会越界崩**：`TOPICS[0][1]` 兜底那行在池子被掏空时 `IndexError`。修法：`load_topics()` 末尾 `return _BUILTIN_TOPICS or list(_SEED_TOPIC)`，取图兜底改 `fallback_q = TOPICS[0][1] if TOPICS else _SEED_TOPIC[0][1]`。
- **验证“双源全空”要可还原**：临时把 `topics.json` 写成 `[]` 并用正则把 `_BUILTIN_TOPICS = [...]` 换成 `[]`，`import` 看 `TOPICS` 是否为种子，**finally 里两个文件都写回原内容**。
- **端到端验证的完整套路**（值得照抄）：用真图集脚本现生成一条 → `--days 0 --dry-run` 看它是否被正确识别为“图集 1，文章 0” → 真跑 `--days 0` → 复查 `topics.json` 少了该词、内置表同步少了、草稿箱回到 0 条。既验了清理脚本，也顺带证明图集脚本未被改坏。
- **cron 的 `no_agent` 脚本用标准库写**（`urllib` 即可，别依赖 venv/requests），凭据从技能目录 `.env` 读；这样包装脚本能用系统 `python3` 直接跑，不挑解释器。
