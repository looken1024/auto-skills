# 公众号图集 / 草稿线的运维记录

源起 2026-10-01~02 的图集线改造（贴图→图文 + 小程序链接 + 换话题池 + 草稿箱大清理）。
> 注：流水线本身的文档在技能 `wechat-ai-publisher`（**用户自有，curator 不能写**）；这里是运维侧的可复用经验。

## 1. 草稿箱批量清理

需求形如“除了最近两天的都删掉”。

1. `POST /cgi-bin/draft/batchget`（`no_content=1`，offset 步长 20）拉全量，每条取 `update_time`（unix 秒）。**`total_count` 与枚举数对得上才说明拉全了**；返回条数封顶 20/页。
2. 按“最近 N 天”切分：`datetime.fromtimestamp(ts) >= now - timedelta(days=N)` 保留。
3. **删之前先分类，把“不是流水线产物”的挑出来保护**：本号图集草稿 = `article_type == "newspic"` 或标题含“图集”；**用户手写的文章草稿 = `news` 且标题里没有“图集”**（本次挑出 14 条：三国/历史/社会类 + 3 条同名的「周末小习惯」）。这批列给用户确认，不自己删。
4. `POST /cgi-bin/draft/delete` 逐条删，`errcode=0` 即成功；每 25 条 sleep 0.3s。**删除不可恢复**。
5. 删完再拉一次 `total_count` 复核。

### 踩坑
- **分类规则别写窄**：第一版过滤器写成“标题含「图集」”，但**老图集草稿的标题就是纯话题名**（“秋天”“森林”“咖啡馆”）→ 只删掉 36/113。正解：`type == "newspic" or "图集" in title`。删前先打印分类清单核一遍。
- **后台页面计数可能对不上 API**：用户看到“还有 142 条”，而 API `total_count=49`（49 草稿 + 已发≈93）。本号 `freepublish/batchget` 报 `48001`，**拿不到已发表列表，验证不了后台那个数**——请用户截图/刷新页面，别硬猜。
- **发布后草稿会从草稿箱消失**：在草稿箱里找不到≠没建过（曾因此误判用户那篇文章“不是我们生的”）。

## 2. `process_image()` 的 OOM（2026-10-02 修，别回退）

- 症状：图集进程 exit `-9`，日志停在“下载完成”之后；`dmesg -T | grep -i "killed process"` 能直接看到。
- 根因：本机 ~2G 内存，原实现对**整图**调 `np.random.normal(..., arr.shape)`——float64 噪声数组在 2500×3750×3 上就是 225MB，加上加法/clip 的临时数组单张峰值 **500MB+**，9 张连跑必死。
- 修法：`float32` + **按行块（band=256）加噪**，`np.clip(..., out=blk)` 原地写，峰值降到 ~150MB/张。
- 运维：跑图集前先 `free -m`；可用内存 <300MB 时先清浏览器残留标签（`curl 127.0.0.1:9222/json/close/<id>`，本次一次关掉 27 个标签回收 ~400MB）。
- 通用教训：这类“图像滤镜流水线”在 2G 小机器上要把**逐像素运算改成分块 + float32 + 原地写**，不要留整图大数组。

## 3. 版式取舍：贴图 vs 图文（已定案）

- 微信草稿 `content` 能力：`newspic`（图片消息/小绿书）**只支持纯文本**；`news`（图文消息）**支持 HTML**。
- 所以“正文里一行字可点击跳小程序”**只能用 `news`**；用 `newspic` 写 `#小程序://` 是死文字。
- 代价：图集从「贴图」变成「图文消息」，版式不同了（用户当时就问过“我原来是贴图，现在怎么变成了图文”）。已向用户说明并确认：“要推小程序链接就只能用图文”。
- 已实测的写法细节（`<a data-miniprogram-appid=...>`、`uploadimg` 取正文图 URL、`draft/update` 不能改类型报 `53403`、`draft/batchget` 才是列草稿接口）见 `references/wechat-draft-api-content-types.md`。
